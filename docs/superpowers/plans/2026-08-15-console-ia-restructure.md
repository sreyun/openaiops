# 新控制台信息架构（IA）重排方案

来源：2026-08-15 产品视角复查留下的第 3 条——「信息架构偏重，新用户『该去哪做某事』基本靠
记忆」。前两条（工单/变更三层无界、告警详情是死胡同）已分别在 `64d1a23` 与本次提交解决；
这一条是重构而不是修 bug，所以先出方案，不动代码。

**结论先说**：问题不在「入口太多」，而在**分组是按「功能是什么」切的，不是按「人在做什么」
切的**。所以入口再少也救不了——真正的成本是一条日常动线要横跨三四个入口，而每个入口里又
藏着十几个并列标签。下面的方案不追求把 23 个入口砍到 10 个（那只会把深度换成迷路），而是让
**每条动线落在一个页面里走完**。

---

## 一、现状（可复现的量化）

```bash
cd frontend
grep -c "path:" src/router/index.ts                     # 路由 30 条
grep -rn "el-tab-pane" src/views/*.vue | wc -l          # 158 → 二级标签 79 个
wc -l src/views/*.vue | sort -rn | head -5              # 最重的几页
```

| 维度 | 数字 |
|---|---|
| 侧边栏一级入口 | 23（概览 + 7 分组 × 22 项，`AppLayout.vue:118` 的 `groups`） |
| 二级标签 | 79 |
| 最重的页 | `SreView.vue` 4085 行 / 13 个一级标签（AI 资产里再套 3 个） |
| 次重的页 | `SettingsView.vue` 2745 行 / 11 标签，`SecurityView.vue` 2535 行 / 10 标签 |
| 表格 | 115 个 |

当前 7 个分组（`AppLayout.vue`）：

| 分组 | 项 |
|---|---|
| observe | 主机、拨测、日志、资源、网络、仪表盘 |
| alerting | 告警、SRE |
| ops | 剧本、端口转发、SQL、API 监控、CI/CD |
| config | 数据源、抓取目标 |
| security | 安全 |
| tools | Hermes、终端、远程桌面 |
| system | 审计日志、系统设置、AI 设置 |

## 二、三个可验证的具体问题

### 1. 分组是能力分类法，不是任务分类法

以「observe / ops / config / tools」这种词分组，是按**这个功能属于什么**命名的。用户脑子里
的问题却是「我现在要做什么」。两者对不上时，用户只能靠记忆。

三条最常见的动线，各自要跨几个一级入口：

| 动线 | 今天要走的入口 | 次数 |
|---|---|---|
| 处置一条告警 | /alerts → /hosts（看机器）→ /sre?tab=incidents（建事件/工单） | 3 |
| 发一次变更 | /sre?tab=changes（申请）→ /automation（跑剧本）→ /sre?tab=changes（回填结果） | 2（来回 3 次） |
| 新装一台机器上线 | /hosts（装 Agent）→ /checks（配拨测）→ /alerts（配阈值）→ /sre?tab=slo | 4 |

第一条昨天已经在告警抽屉里补了「查看该主机 / 打开终端」，把 3 步压到 1 步——**那就是这份
方案要在结构上系统做的事**，抽屉只是其中一个点。

### 2. SreView 一页装了四类不同东西

13 个并列标签，按角色和时间尺度至少是四类：

| 类别 | 标签 | 什么时候用 |
|---|---|---|
| 救火（分钟级） | 事件、值班、自愈、效果 | 出事的时候 |
| 流程（天/周级） | 工单、变更、SLO、巡检 | 排期做的事 |
| 资产（月级） | 服务、拓扑 | 建档时维护 |
| AI 运维 | AI 助手、AI 资产（运行/技能/记忆） | 任何时候 |

它们共用一个 4085 行的组件、一份 `tab` 状态、一个懒加载分块。救火的人要在 13 个标签里找
「事件」，而旁边就是「AI 技能库」。

### 3. 一半带标签的页面没有深链，标签选不中就分享不了

`?tab=` 同步过的：`AlertsView`、`CicdView`、`SettingsView`、`SreView`、`ChecksView`、
`NetworkView`、`ResourcesView`、`SecurityView`（8 个）。
**没同步的**：`K8sView`、`SqlView`、`TerminalView`、`ScrapeView`、`AutomationView`、
`ApiMonView`、`AiSettingsView`、`ForwardView`（8 个）。

后果很具体：值班群里发不出「你看这个页」的链接，只能口述「进 XX 页，点第三个标签」。

### 4. 顺带发现：两个并存的 AI 对话入口

`/hermes`（`HermesView` + 全局 dock，走 `hermesApi`）与 `SreView` 的「AI 助手」标签
（自己一套消息状态，走 `POST /ai/assist` 流式）是**两套实现、两个后端**。功能对错上都没
问题，但用户没有办法判断该用哪个。这条不在本方案的必做项里（合并要先定后端归一），但
IA 上必须承认它是重复入口。

## 三、方案

### 原则

1. **一条动线落在一个页面里走完**，跨页面的地方用深链 + 抽屉动作补，而不是让用户自己导航。
2. **分组名用动词或场景名**，不用能力名。
3. 拆页面只拆「不同时间尺度 / 不同角色」的，不拆「同一件事的不同视图」。

### 一级导航：7 组 → 5 组

| 新分组 | 项 | 变化 |
|---|---|---|
| 概览 | 概览 | 不变 |
| 监控 | 主机、仪表盘、拨测、日志、资源、网络、API 监控 | API 监控从 ops 移入（它就是监控） |
| 处置 | 告警、**事件中心**（新，拆自 SRE）、终端、远程桌面、剧本 | 救火要用的东西收在一起 |
| 流程与资产 | **工单与变更**（新，拆自 SRE）、**服务与拓扑**（新，拆自 SRE）、CI/CD、SQL | 排期做的事 |
| 安全 | 安全 | 不变 |
| 系统 | 数据源、抓取目标、端口转发、审计日志、系统设置、AI 设置（含 AI 资产） | AI 资产从 SRE 移入 |

一级入口数 23 → 24（几乎不变），但**每个入口名字都是用户能自己说出来的名词**，而不是
「SRE」这种要先学会才能用的缩写。这个取舍是刻意的：把深度换成宽度，不是把宽度砍掉。

### SreView 拆分

| 新路由 | 收哪些标签 | 预估行数 |
|---|---|---|
| `/incidents` 事件中心 | 事件、值班、自愈、效果 | ~1200 |
| `/workflow` 工单与变更 | 工单、变更、SLO、巡检 | ~1400 |
| `/cmdb` 服务与拓扑 | 服务、拓扑 | ~600 |
| `/ai-settings` | AI 资产（运行/技能/记忆）并入现有 AI 设置页 | +700 |
| `/hermes` | AI 助手标签并入（**待定**，见问题 4） | — |

`/sre` 保留为**重定向路由**：`/sre?tab=tickets` → `/workflow?tab=tickets`，逐标签映射。
旧链接（值班群里、书签里、告警通知里）必须继续能打开，这是硬要求。

### 二级标签统一深链

给还没有的 8 个页面补 `?tab=` 双向同步。这一步与拆分无关，可以先做、单独发。

## 四、分阶段

| 阶段 | 内容 | 风险 | 判据 |
|---|---|---|---|
| Phase 0 | 8 个页面补 `?tab=` 深链 | 极低，纯增量 | 每个带标签页面刷新后停在原标签；`npm run check` 绿 |
| Phase 1 | 一级分组重排（只改 `AppLayout.vue` 的 `groups`，不动路由） | 低，可一键回滚 | 导航折叠状态 `localStorage` 键仍能读（分组 id 变了要迁移，见风险） |
| Phase 2 | SreView 拆 3 个路由 + `/sre` 重定向 | 中，是真重构 | 旧 `?tab=` 链接全部可达；`check:entry-weight` 不超 200 kB |
| Phase 3 | AI 资产并入 AI 设置；两个 AI 对话入口归一 | 中高，涉及后端归一 | 先定后端，再动前端 |

Phase 0 和 1 是几小时的事，Phase 2 需要一天且必须逐标签核对。**建议按阶段分别发版**，
不要合成一个大 PR——IA 改动最需要的是能单独回滚。

## 五、风险与约束

- **旧链接**：`/sre?tab=xxx` 出现在告警通知模板、审计记录、用户书签里。Phase 2 必须带
  逐标签重定向表，且保留至少两个小版本。
- **导航折叠状态**：`AppLayout.vue` 用 `NAV_COLLAPSED_KEY` 在 `localStorage` 里存**分组 id**。
  Phase 1 改了 id，老用户的折叠状态会失效（表现为分组全部展开）。要么保留旧 id，要么写一次
  性迁移。
- **`check:parity` 不受影响**：它比对的是「经典控制台调用的 API 在新控制台有没有等价调用」
  （`scripts/audit-legacy-api-parity.mjs`），是 API 级不是 UI 级。改 IA 不动接口就不会红。
- **`check:entry-weight`**：首屏预加载 gzip 预算 200 kB，禁止 echarts/xterm 进入口图。拆
  SreView 会新增 3 个懒加载分块，正常不会碰预算，但 Phase 2 结束必须跑一次 `npm run build`
  + `npm run check:entry-weight` 确认。
- **i18n**：新增分组名与页面名要三语齐全（`zh-CN` / `zh-TW` / `en`），否则 `check:i18n` 卡门禁。
- **经典控制台不跟随**：`cmd/server/web/` 是出厂控制台，本方案只针对 `frontend/`。两边 IA
  会因此拉开差距——这是既有事实（新控制台本来就是重做的），但要在发布说明里讲清楚。

## 六、明确不做

- 不砍功能。79 个二级标签背后都有真实功能，问题是排列不是数量。
- 不做「自定义导航」这类让用户自己整理的功能——那是把设计问题转嫁给用户。
- 不在这一轮动 `SettingsView`（11 标签）和 `SecurityView`（10 标签）。它们同样重，但设置类
  页面「一次配置、长期不看」，动线成本远低于 SRE 页，排在后面。
