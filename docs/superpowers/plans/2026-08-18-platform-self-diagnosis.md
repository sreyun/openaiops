# 平台给自己看病：把自身故障做成「和别人的故障同一种东西」

承接 `2026-08-18-windows-agent-update-version-probe.md`。

那件事真正暴露的问题，不是探针写错了一行判据，而是：**平台一直知道答案，却没有任何
一条路径把答案送到人面前。**

- 失败原因一直在，就写在主机本地的助手日志里；
- 「它在重复失败」这件事一直在，就摆在五条一模一样的记录里；
- 可这两条信息都没有走进「事件 → 诊断 → 处置 → 回验」那条链。

于是一个能被一句话定位的问题，拖成了「Windows 升不上去，谁也说不清原因」，最后靠人
登上那台机器把日志贴出来才结束。

## 一、结构性的不对称

平台对**别人**的故障有完整闭环：

```
告警 → 事件 → AI 自动诊断 → RAG 相似案例 → 拓扑 RCA → 值班指派
     → 结论转动作（工单/自愈/关联变更）→ 客观回验 → 回流记忆
```

对**自己**的故障只有一行 `slog`：

| 自身故障 | 原来的全部处理 |
|---|---|
| 常驻循环 panic | `slog.Error` + 5 秒后重启 |
| VM 写入队列满、样本被丢 | `slog.Warn`（每 200 次一条） |
| VM 拒绝写入、整批丢弃 | `slog.Warn`，**且响应体直接倒进 `io.Discard`** |
| 审计链追加失败 | `slog.Warn` |
| Agent 升级连续失败 | 一条会被下一次覆盖的记录 |

日志是给**已经知道要查什么**的人看的。不知道该查什么的时候，日志等于不存在。而
「监控自己坏了」恰恰是唯一一种不会有人来告诉你的故障——所有本该报告它的通道，正是
坏掉的那个东西。

## 二、做法：不新建闭环，而是把自身故障塞进现有闭环

新增 `cmd/server/self_fault.go`，一个入口：

```go
s.reportPlatformFault(component, kind, level, hostID, message, evidence)
```

它做三件事：

1. **按指纹聚合**。复用 `agentUpdateFailFingerprint`（抹掉时间戳、pid、哈希、数字）。
   自身故障最典型的形态就是同一件事每分钟发生一次，逐条落库只会把信息淹掉。指纹里
   带 `hostID` 是有意的：同一个原因发生在两台机器上是两件事——一台机器的问题，和一批
   机器的问题，规模本身就是信息。
2. **按条件开事件**。`critical`（panic、审计链断）第一次就开；`warning` 连续 3 次才开；
   同一条故障只开一个事件，绝不重复。隔 30 分钟以上再出现算「新的一串」，计数重来——
   一条每天出现一次的偶发故障，攒上一周也不该假装成「连续失败」。
3. **把证据挂到事件时间线**。AI 诊断读的就是时间线，证据不进去等于没采集。

用的是和主机故障**完全同一个** `incidents.raise`，所以它自动获得消息中心、AI 自动诊断、
RAG 相似案例关联、拓扑 RCA、值班指派、结论转动作与客观回验——**一行都不用重写**。
`warning` 级额外补一次 `autoDiagnose`（原链路只对 critical 开），因为自身故障往往横跨
多个子系统，人不一定知道该从哪查起，正是最该让 AI 先看一眼的一类。

## 三、已接入的来源

| 来源 | 级别 | 为什么是它 |
|---|---|---|
| `superviseLoop` / `safeGo` 的 panic | critical | 一条常驻循环反复崩溃 = 某个监控能力已经静默失效 |
| VM 写入队列满、丢样本 | warning | 丢点就是曲线上的洞，而洞不会说自己怎么来的——「历史曲线看不到」那一类现象的根因 |
| VM 拒绝写入（4xx，整批丢弃） | warning | 见下：这次顺带把**唯一解释原因的那段文字**救了回来 |
| 审计链追加失败 | critical | 页面照常、告警照常，只有事后取证才发现链上缺了一段，而那时已无从补起 |
| Agent 升级连续同因失败 | warning | 这套机制的起因 |

### 顺带修掉的一处「证据被丢弃」

`vmImportDone` 在 4xx 分支里把响应体直接 `io.Copy(io.Discard, …)`。而 VM 在 4xx 里写的
正是**哪一条样本为什么非法**（非法标签名、超长标签值、NaN），这批数据接下来就被丢掉。
把唯一解释原因的那段文字扔掉，等于让「一条坏样本把整台服务器的时序写入堵死」这件事
永远查不出是哪条样本。现在它被读出来，进日志、也作为证据进事件。

这与「Windows 失败详情截到 160 字」「AI 操作审计详情截到 120 字」是同一个缺陷的第三次
出现，因此值得写成规矩：**证据在抵达人眼之前不得被截断或丢弃。**

## 四、AI 侧：先排除平台自身

新增工具 `query_platform_faults`（`sreyun_platform.go`），并放进 MCP `sre` 只读白名单。

此前 AI 对话里能问遍主机、容器、K8s、告警、事件，唯独问不到「平台自身有没有出问题」
——而排障时这恰恰是要先排除的一项：

- 指标断了，是主机没上报，还是写入泵在 panic 重启？
- 升级没动静，是没触发，还是连续失败被熔断了？
- 曲线有洞，是采集侧的问题，还是 VM 拒了那一批？

没有这个工具，AI 只能从「别人的症状」倒推，答不到根因上。工具描述里写明了「排查
监控/告警/升级/曲线本身不工作时先用本工具」，并把 `count`、`incident_id` 一并带出，
AI 拿到之后可以直接 `diagnose_incident` 深入，或把结论一键转成工单（既有 `/ai/followup`）。

## 五、回归测试

| 测试 | 断言 |
|---|---|
| `TestPlatformFaultAggregatesByFingerprint` | 同因聚合成一条并累加；不同原因分开 |
| `TestPlatformFaultRaisesIncidentAtThreshold` | 未到阈值不开事件；到阈值开且回填 incident_id；再来 100 次仍只有一个事件 |
| `TestPlatformFaultCriticalRaisesImmediately` | critical 第一次就开；**证据出现在事件时间线上** |
| `TestPlatformFaultStreakResetsAfterGap` | 隔 30 分钟以上再出现，计数重来 |
| `TestSupervisedPanicBecomesPlatformFault` | panic → loop/critical 故障 + 堆栈作为证据 + 开出事件 |

## 六、后续可接的来源（尚未接）

按「静默时会造成用户可见谜团」排序，下一批值得接的是：Flow 入库队列满丢批、
PG 写告警历史失败、通知渠道连续发送失败、AI 调用连续失败、扫描任务连续超时。
接法都一样：在已有的 `slog.Warn` 旁边加一行 `reportFault`，成本极低。
